# 上游跟进与版本发布契约

状态：r2 已确认策略。上游新能力经适配和回归后随 APK 发布。本文定义后续实施所需的差异检查和发布流程，不表示自动检查工作流已经部署。

## 复用边界

维护未修改的 upstream tree、清晰的宿主补丁集与锁定清单。HyperBackup 必须实际调用上游业务执行主线；只打包 speednative、Dex、tar/zstd，再自行重写应用备份/恢复/上传，不满足长期完整跟进目标。

允许的适配集中在宿主身份、Root 启动、选择/表单响应、类型化 operation 路由、观察/取消、任务关联、路径映射和附加索引。业务修复确需偏离上游时记录原因、测试、上游来源与撤销条件，避免变成难以同步的大型 fork。

App 对外保持稳定 operation ID。上游菜单 ID 来源于行号，不能硬编码为长期产品 API；每个支持 SHA 都核验 operation→上游执行入口和参数映射。新配置可借助元数据生成 Miuix 表单，但复杂交互与新数据类型仍需独立适配。

## 每个版本的锁定资料

- upstream repository URL、完整 commit SHA、标签/发布标识和源代码校验信息。
- versions.properties 的 build/script/Dex/各 applet 版本；组件版本不要求数值相同，要与该 SHA 的配套清单相符。
- 原始产物、重建产物、补丁集与最终 APK 的 hash，工具许可及源码构建对应关系。
- 宿主 package/signing 身份、bridge protocol、菜单/操作映射、配置 schema/default 快照、所需 capabilities。
- 可读/可写备份格式及双向恢复测试对应的上游版本、已知平台限制、功能矩阵证据。

## 变化来源

| 检查源 | 至少比较 |
| --- | --- |
| README、版本/发布说明 | 可见能力、限制与迁移说明 |
| tools/tools.sh 菜单与 commands_data | 新增/删除/移动操作和真实分发变化 |
| 设置模板、runtime_conf、settings-labels/options | 字段、枚举、默认值、语义、废弃与迁移 |
| Dex/Rust capabilities 与自检 | 运行契约、工具要求、版本握手 |
| 备份/恢复/安装/传输/清理代码 | 行为修复、特殊路径、错误码和失败收尾 |
| 格式解析与 sidecar、源测试 | metadata、Timeline/communications 等数据兼容性 |
| source-package.json、embedded metadata、构建/更新脚本 | 配套资源、宿主身份、产物与来源一致性 |

只看 release 号或 README 会漏掉实际代码能力。差异报告只能发现需要处理的项目，不能直接证明 UI 或恢复已兼容。

## 候选到正式版

1. 检查新上游候选，与当前支持 SHA 生成固定差异报告；记录新增能力、删除项、默认值变化、格式变化、行为修复。
2. 更新覆盖矩阵，为每一差异作分类。未分类差异阻断将候选声明为受支持版本；源真正删除的能力按迁移说明处理，不假装仍由新版提供。
3. 重放最小宿主补丁并审查冲突；构建完整配套 Shell/Dex/native 工具。禁止只换一个文件造成混用版本。
4. 运行上游检查，加 HyperBackup 的协议、Miuix交互、安装/恢复故障和双向格式回归。对修复进行定向回归，对 schema/默认值变更进行历史样本回归。
5. 生成受支持版本清单、覆盖结果和已知限制；全部门槛通过才随 HyperBackup APK 发布。未通过只能为测试候选，不能运行时偷换正式工具。
6. 安装后仅在无活动任务且上一次结果已对账时激活配套引擎；失败保留已知可用版本和可解释状态。App 更新可能杀死 daemon，不能依赖 onDestroy 完成迁移。

实施应提供可重复运行的 upstream audit（本地/CI、手动触发及发布必跑），将差异报告作为构建产物。若以后启用定时扫描，它只发现和报告差异，不自动发布、覆盖运行引擎或把新字段静默启用；不在此设计阶段擅自创建外部定时通知。

## 原始更新路径必须适配

固定源 tools.sh:22705–22802 会剪裁/同步 tools 并重建 start/recover/backup/upload 入口；未登记的桥接文件可能被删除。Dex AppListReturn.java 的原包名/签名/APK hash 与 rust/applist_web.rs 的安装路径还可能安装、启动原 SpeedBackup。

因此 HyperBackup 更新入口应检查并获取已验证的 HyperBackup APK，沿用对应的校验与失败保护目的；不能把原始脚本 ZIP 原样覆盖到 App 运行目录。备份附带的兼容恢复工具与 App 私有桥接资源分开管理，互操作测试必须覆盖上游启动器和更新器。

源设置迁移同样需复用字面值解析与模板同步规则；不能 source 任意外部配置，也不能只“补新字段”却保留已被源删除的公开键。

## 关键验收

- 上游新增一行菜单不会使旧 operation ID 调错业务；新增设置默认值不会被 App 老默认覆盖。
- 补丁与完整工具能够从锁定源码重建；纯 UI 更新不改变备份/恢复策略。
- 旧源→新 App、新 App→对应原脚本、前一支持版本→新版本都按声明的数据类型通过。
- 更新不安装/唤起原 SpeedBackup，不删除 App 桥接和附加元数据，不在进行中的备份集里替换工具。
- 覆盖矩阵里没有入口、实现或测试证据的必需能力阻断正式发布；明确列出测试设备覆盖，不能以一台设备证明全平台。
