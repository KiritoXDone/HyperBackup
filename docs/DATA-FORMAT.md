# 上游兼容备份集与附加元数据

状态：r2。本文替代 r1 的 App 专用 record.json 容器；用户确认与声明支持的上游版本双向兼容，并同时提供新建/更新备份集，默认新建。未来脚本版本不被自动包含在兼容承诺中。

## 数据权威与模型

| 对象 | 含义与权威 |
| --- | --- |
| BackupSet | 一份可由原脚本识别的备份根与其内容；载荷和原生 metadata 由上游流程产生 |
| BackupBatch | 一次执行的目标与结果；可能新建集，也可能更新集 |
| BackupRepository | App 管理的备份集/位置集合，不要求每个脚本目录带 App 自有仓库标记 |
| AppInstance / BackupObject | 当前用户/包身份，或 Wi-Fi、通信记录、文件夹等类型化对象 |
| AndroidUserMapping / AccountMapping | Android 用户映射与 Timeline 等账号映射分开，不能用同一个整数替代 |
| Task / TaskItem / OperationPlan | App 对不可变操作计划、观察记录及实际结果的管理，不冒充源备份格式 |
| AuxiliaryIndex / DigestRecord | 可重建、可失效的索引与检查证据，不是原脚本恢复必需条件 |

来源用户 ID 不照抄为目标 UID。每次写入按引擎解析目标用户、应用和账号。一个应用恢复计划不得同时把多个版本写向同一个 targetUserId/packageName。

## 保留原布局

代表性布局由上游生成，以下只示意兼容层次，不能代替所有特殊类型的实际格式：

```text
<用户选择的位置>/
  Backup_<compression>_<user><suffix>/
    <上游命名的应用目录>/
      app_details.json
      apk.*
      user.*
      user_de.*
      ...上游产生的归档与特殊载荷...
    app_details_bundle.tar.zst   # 远端 metadata 主路径，按模式/源规则存在
    Media/
    wifi/
    communications/
    ...上游工具/恢复入口及其他原生产物...
```

不得将应用再套入 batches/<batchId>/apps/<recordId> 后仍宣称原脚本可读。不得任意重命名应用目录、metadata bundle 内路径、Timeline/communications sidecar 或恢复入口。具体由脚本生成的内容、大小和保留规则优先于示意图。

## 双向兼容

1. 原脚本→App：识别当前格式以及该支持版本能读取的旧格式，沿用本地旧 JSON 转换和远端 bundle-only 规则。不因缺少 App 索引/hash/COMMITTED 文件拒绝原备份。
2. App→原脚本：App 输出的备份集由对应未修改的原脚本识别并恢复；关键对象不能只能在 App 中打开。
3. 历史与升级：以测试样本声明兼容范围，不承诺任意旧版或未知未来版。未来格式未知时只读展示错误，禁止猜测转换或覆盖。
4. 去掉附加元数据后仍可按原脚本恢复。附加层失效时重建索引，不修改原 payload 来“修复索引”。
5. 兼容判据不仅是同为 tar/zstd：必须核验扫描、目录/metadata、选择、安装、数据恢复、特殊对象、上传、清理与附带恢复工具。

## App 附加层

任务、来源标识、用户标签、hash、检查时间、操作日志与连接凭据引用先保存在 App 私有数据。需要随备份迁移的非敏感附加元数据，放在与原备份根分离的伴随位置；位置必须经过上游扫描、统计、上传、清理、恢复和更新测试后确定，不能仅假设“隐藏目录会被忽略”。

附加层用对象路径及源 metadata/内容身份映射稳定 App ID。复制/更名后重新识别；不能只凭文件名判断对象没有变化。凭据不在该附加层导出。识别不到附加层时仍可列出原生备份集，再补建索引。

原生备份是否有效遵循上游检查结果。App 可以保留未完成操作和临时文件日志，但不能要求原脚本认识 App 的提交标记，也不能将缺少 App 标记等同于脚本备份损坏。

## 新建、更新与版本

新建为默认：使用唯一且符合上游规则的 suffix/目标根，先检查冲突；时间到秒的后缀不足以独自保证唯一。以前的备份集保持原样。

更新已有集：明确目标，执行上游原有比较、fast-skip、产物更新和 metadata 更新；UI 显示“更新已有备份集”，不得把批次历史误说成可恢复的内容版本。用户可选择先新建一集再进行另一项更新，但 App 不暗中复制或硬链接数据来假装零成本不可变快照。

通信记录的特定世代保留、日志容量清理和孤儿清理按其独立规则执行并说明影响范围。不能因为 App 支持多个备份集就替换这些源规则，也不能把它们描述为通用保留策略。

## 校验与模式

| 模式/证据 | 可声明 | 不可声明 |
| --- | --- | --- |
| 识别 metadata | 已识别备份集和所列对象 | 所有归档完整 |
| 沿用源清单/结构/大小检查 | 所列检查通过 | 所有文件内容 hash 已核验 |
| 新产物生成附加摘要 | 已记录摘要；是否回读另列 | 远端所有字节已回读 |
| 下载后摘要匹配、结构检查通过 | 该归档内容比较与结构检查通过 | 应用必然免登录/适配所有 ROM |
| 没有历史摘要的脚本备份 | 采用上游支持的检查，摘要缺失说明 | 用刚计算的摘要证明历史内容未变 |
| 直接串流恢复 | 按上游流式校验/收尾记录真实结果 | 完整归档检查已在覆盖前结束 |

远端备份需保留流式、非流式、逐应用上传及本地保留选项。默认恢复采用下载后恢复，直接串流恢复可显式选择。流式失败可能已写入目标；检查结论、已写入阶段与恢复前副本分别呈现。

## 恢复前副本和故障

应用恢复默认创建上游兼容的恢复前备份集或对应兼容副本，关联恢复任务作为附加信息；用户可明确关闭。副本按实际将改动范围保存，不用只含 APK 的产物充当数据保护。提交/保存未确认成功不得覆盖对应应用。

原来源只读或空间不足时明确选其他可写目的地或关闭副本，不悄悄降级。默认下载模式需要计算当前归档暂存、展开后占用、保护副本及安全余量；直接串流仍需展开后的空间和 metadata，不标成零空间。

应用更新失败但继续数据、提交未知、冻结/暂停收尾等结果由原业务流程提供，App 保守对账。没有跨整个恢复过程的自动回滚承诺。

## 并发与删除

App 内修改作业互斥。外部原脚本不会自动遵守 App 锁，因此提交前/修改前检查源文件变化，遇到并发或状态未知停止并解释；声明单写者限制，不能把一个私有 writer-claim 文件当成跨工具互斥证明。

保留原脚本手动删除、孤儿候选与修复的业务行为；在 App 确认页显示实际对象、备份集和不可撤销影响。活动作业引用的备份不能被本 App 删除。清理后附加索引对账，不能为了索引一致性额外删除原脚本未选中的内容。

## r1 预览产物

若开发预览已经产生 App 专用容器，识别它为不兼容预览格式，提供明确错误或另行设计的导出迁移。不得静默把它当正式原生备份，不能为照顾未发布预览而继续把正式格式绑定到旧容器。

兼容样本、故障注入及原脚本互操作的验收见 [验证计划](VALIDATION-PLAN.md)。
